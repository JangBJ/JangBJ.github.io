RENTO 는 Gradle 멀티모듈입니다. 처음부터 이렇게 시작한 건 아니고,
단일 애플리케이션으로 만들다가 중간에 쪼갰습니다.

```text
rento-mm
├── rento-api    관리자용 REST API (차량 · 운행 · 통계 · 지오펜스)
├── rento-pub    차량 단말이 이벤트를 쏘는 수집 엔드포인트
├── rento-sub    큐에서 이벤트를 꺼내 처리하는 소비자
├── domain       엔티티 · 도메인 서비스
├── infra        JWT · 시큐리티 · 외부 연동
└── common       공통 유틸 · 예외
```

## 갈라야 했던 이유

`rento-pub` 과 `rento-api` 는 들어오는 트래픽의 성격이 완전히 다릅니다.

| | rento-pub | rento-api |
|---|---|---|
| 호출 주체 | 차량 단말 (자동) | 관리자 (사람) |
| 호출 빈도 | 주기적, 차량 수에 비례 | 간헐적 |
| 요청 내용 | 쓰기 위주, 작은 페이로드 | 읽기 위주, 조인 많은 쿼리 |
| 느려지면 | 데이터가 유실됨 | 화면이 느려짐 |

한 프로세스에 같이 두면 통계 화면에서 무거운 집계 쿼리 하나 돌 때
단말 수집까지 같이 밀립니다. 수집은 밀리면 그 시점 데이터가 그냥 사라지는 쪽이라
둘을 같은 스레드풀에 태우고 싶지 않았습니다.

반대로 **도메인 모델은 공유해야** 했습니다. 단말이 보낸 주기 데이터를 해석하는 규칙과
관리자 화면이 그걸 읽는 규칙이 달라지면 안 되니까요.
그래서 실행 단위(`api` / `pub` / `sub`)만 나누고 `domain` 은 하나로 뒀습니다.

## 얻은 것과 치른 값

얻은 것은 **배포 단위의 독립**입니다. 관제 화면 쪽을 고쳐 배포해도 수집은 안 끊깁니다.

치른 값은 **모듈 경계를 계속 신경 써야 한다**는 것이었습니다.
`common` 에 뭘 넣을지 `domain` 에 뭘 넣을지가 매번 애매했고,
편하다는 이유로 `domain` 이 점점 비대해지는 걸 몇 번 되돌렸습니다.

지금 다시 한다면 모듈을 나누기 전에 **패키지 레벨에서 먼저 경계를 그어 보고**,
그 경계가 실제로 지켜지는 걸 확인한 다음에 모듈로 승격시킬 것 같습니다.
